# ПРОЕКТНЫЙ СЛОЙ ВОРКФЛОУ — Dajet

Канон команды живёт в репо **bestdeejay-design/agents** (эталон) и его копии в
`workflow/` этого репо (PROTOCOL, WORKFLOW, BUS, BOARD, OPS, AGENT_RULES,
COORDINATOR_RULES, KNOWLEDGE_BASE, EXAMPLES, шаблоны). Этот файл — только
проектная конкретизация: что в Dajet работает иначе или дополнительно.

## Состав контура

| Репозиторий | Видимость | Роль | Шина |
|---|---|---|---|
| `dajet/player` | публичный | основной продукт (плеер) | **issues здесь** |
| `dajet/ui` | приватный | общий пакет дизайна `DajetUI` — дизайн-система контура | issues в `dajet/player`; доступ к репозиторию даёт владелец |
| `dajet/editor` | приватный | редактор (дерево, tree-sitter) | issues в `dajet/editor` |
| `dajet/browser` | публичный | витрина/лендинг | отдельной шины нет |

Шина контура — GitHub issues `bestdeejay-design/dajet-player`. Канонические 52 labels
созданы в `dajet-player` и `dajet/ui` (`workflow/create-labels.sh`, идемпотентно).

## Роли и каналы

| Узел | Канал |
|---|---|
| Владелец (bestdeejay-design) | продуктовые решения, развилки, приёмка, ручной запуск внешних сессий |
| Координатор (куратор контура) | очередь, issues с брифом и радиусом, гейты, PR, слияния, независимая проверка на своей машине |
| Арена — внешний исполнитель | **запись в issues есть**: пуш своей ветки `arena/<session-id>-…` + письмо-комментарий в issue |
| SZ (super-z) — ревью и инженерия | запись в issues есть; крупные задачи, read-only аудиты, независимая верификация |

Подпись узла обязательна в каждом сообщении («— Роль · сессия»): все работают под
аккаунтом `bestdeejay-design`, личность живёт в подписи, а не в поле автора.

## Проектные постоянные

- **Порядок волн** — эпик `dajet/ui/docs/BACKLOG-PRE-RELEASE.md`:
  **G2 → P1 → P5 → P2+P3 → P4 → P6 → P7 → B-волны → E-волны.**
  G2 (пакет дизайна) и P1 (одна ось темы, `Look` из пакета) сделаны. Следующая — **P5
  «Материалы по Apple»**.
- **Приёмочная точка P5** — окно на обоях владельца. Отчёт исполнителя доказательством
  не считается: смотрит владелец, на своей машине, глазами.
- **Path-зависимость `../ui`.** `dajet/player/Package.swift` тянет локальный пакет:
  `.package(path: "../ui")`, цель `DajetPlayer` → продукт `DajetUI`. Локально работает
  (пакет лежит рядом), в CI пакет надо доставлять отдельным checkout — задача владельца
  на способ доставки (видимость `dajet/ui` или токен в секретах репозитория).
- **Приватность `dajet/ui`.** Пакет приватный; внешние агенты без выданного владельцем
  доступа его не видят. Доступ к приватным репозиториям даёт владелец.
- **Слияние в `main` редактора — только владелец** (`dajet/editor/AGENTS.md`). То же для
  неслитых коммитов в редакторе: пока владелец не сказал — не мержим.
- **Zero-dependency — принцип серии:** только фреймворки Apple. CI проверяет пустой
  `.build/checkouts` и отсутствие сетевого кода в `Sources`.
- **Регресс плеера (канонический порядок):** `swift build` → `swift test` → `./build.sh`.
  Бюджет бандла — 15 МБ. CI (`build.yml`, macos-15) зелёный — гейт слияния.
- **Артефакты приёмок** — `dajet/player/artifacts/YYYY-MM-DD-<тема>/README.md`.
- **Гигиена веток:** слитая ветка удаляется; отработавшее — тегом `archive/*`; база
  поставки — свежий `origin/main`.

## Соответствие статусов (шина ↔ борд)

| Колонка борда | Label шины |
|---|---|
| Бэклог | `status:inbox` |
| Ждёт | `status:blocked` |
| К работе | `status:ready` |
| В работе | `status:in-progress` (+ `phase:*`) |
| На проверке | `status:review` |
| Правки | `status:rejected` |
| На приёмку | `status:review` + `needs-human` |
| Готово | `status:done` + issue закрыт |

**Борд (GitHub Projects) для Dajet не настроен и недоступен координатору:** у рабочего
токена нет scope `project` (`users/…/projects` → Not Found). Пока владелец не даст
scope — статус ведётся в labels issues плюс `apps/HANDOFF.md` в контуре. Разъезда
«labels — правда, Projects — вид» тут не возникает: Projects просто нет.

## Прочее

- **Машина у координатора.** У внешних агентов нет доступа к Mac владельца: всё, что
  требует живого приложения (сборка, запуск, скриншоты, двойной клик по файлу в
  Finder), проверяет координатор. Отчёт агента — не доказательство; доказательство —
  прогон координатора.
- **Проблема двойной роли «ревью — не автор»:** ревью волны всегда делает другой узел,
  чем автор. Пост-сливные проверки (например, ревью P1, ушедшей в `main` без
  независимого ревью) оформляются отдельной задачей, а не пометкой в старой.
- **Вопрос ≠ переделка.** Спорное и неоднозначное — вопрос координатору (`❓ QUESTION`),
  а не молчаливая правка кода.
