# AGENTS.md — протокол работы агентов проекта Dajet

**Действует с 31.10.2026. Заменяет прежние неформальные договорённости.**
Каждая холодная сессия агента начинает с: (1) этот файл, (2) `workflow/PROJECT.md`
(проектная конкретика), (3) `git fetch --prune` и `git status -sb`.

---

## 0. Стартовая последовательность

1. `AGENTS.md` (этот файл) → `workflow/PROJECT.md`.
2. Регламент команды — `workflow/`: `PROTOCOL.md`, `WORKFLOW.md`, `BUS.md`, `BOARD.md`,
   `OPS.md`, `AGENT_RULES.md`, `COORDINATOR_RULES.md`, `KNOWLEDGE_BASE.md`, `EXAMPLES.md`.
3. `git fetch --prune` → `git status -sb` → `git log --oneline -5 origin/main`.
4. Найти свою задачу: issue, который тебе поставил координатор (см. §3).
   Нет назначенной задачи — работы нет: спросить координатора, а не искать занятие.

Приоритет документов: **прямое слово владельца** → этот файл → `workflow/PROJECT.md` →
`workflow/*` (общий канон). Канон команды в `agents` — эталон; копия в `workflow/`
взятена из него, при расхождении эталон главнее.

## 1. Роли

| Роль | Кто | Полномочия |
|---|---|---|
| **Владелец** | bestdeejay-design | Приоритеты, продуктовые решения, развилки, финальная приёмка, ручной запуск внешних сессий. Единственный, кто может менять этот протокол. |
| **Координатор** (куратор контура) | Mavis | Единственная точка входа для задач. Превращает решения владельца в issues с брифом, критериями приёмки и радиусом аудита. Назначает исполнителя и ревьювера. Двигает статусы, открывает PR, сливает в `main`, ведёт очередь и статус-карточку. |
| **Исполнитель** | Арена, SZ | Работает ТОЛЬКО в своей ветке поставки. Не пишет в `main`, не мержит, не двигает статусы, не берёт задачи кроме назначенных координатором. |
| **Ревьювер** | любой агент, **не автор** работы | Проверяет поставку до приёмки: код + документация + регресс. Вердикт — в issue. |

Жёсткие правила:

- **Задача исполнителю — только через координатора.** Слово владельца, написанное
  напрямую исполнителю, не является задачей: координатор оформит её в issue, и только
  тогда работа легальна.
- **Поставка — никогда в `main`.** Только ветка + письмо.
- **Приёмка финальная — у владельца**, ревью — у ревьювера, слияние — у координатора.
- **Отчёт исполнителя — не доказательство.** Доказательство — независимый прогон
  координатора: у него есть Mac, у внешних агентов нет.

## 2. Веточная модель

- `main` — канон. Пишет туда только координатор (слияние принятого, откаты, доки).
- **Каждый исполнитель пушит в ветку своего контура.** У Арены платформа жёстко
  привязывает сессию к ветке `arena/<id>` — это её норма, координатор не диктует имена.
  Требования к ветке поставки: не `main`, база от **свежего** `origin/main`, в письме
  о поставке объявлен **диапазон коммитов (хеши от–до)**.
- Самопроверка базы до первой строки кода: `git merge-base HEAD origin/main` == кончик
  `origin/main`. Красный гейт по базе = старая база, а не баг.
- Перед пушем: `git fetch`; `main` уехал — rebase и полный регресс заново.
- **PR открывает координатор.** Право комментировать issues у Арены и SZ есть, право
  открывать PR и мержить — нет.

## 3. Жизненный цикл задачи

```
Владелец → Координатор (issue: бриф + критерии + радиус + исполнитель + ревьювер)
         → Исполнитель (ветка + регресс + пуш + письмо)
         → Ревьювер (вердикт: approve или нумерованные правки)
         → Координатор (PR, слияние, регресс на результате слияния)
         → Владелец (приёмка)
```

### 3.1. Поставка исполнителя = письмо
Письмо — комментарий в issue (у Арены и SZ есть запись в issues). Формат — по шаблону
`📬 DELIVERED` из `workflow/AGENT_RULES.md` §4.4: что сделано / как проверено /
диапазон коммитов / что красное и почему / хеш ветки. Координатор узнаёт о работе по
письму, а не по `git fetch`.

### 3.2. Ревью — обязательный второй заход (двухглазая приёмка)
Ревьювер — **другой агент, не автор**. Проверяет по чек-листу:

1. **Соответствие брифу** — сделано ли ровно то, что в issue; ничего сверх.
2. **Код** — границы задачи (не тронуто чужое), дубли, мёртвый код, отсутствие сети
   (zero-dep — принцип серии), консистентность `Look`/темы с пакетом `DajetUI`.
3. **Документация** — если меняется поведение, обновлены ли README/README.ru/ROADMAP/
   CHANGELOG; письмо поставки полное, статусы честные.
4. **Регресс на ветке исполнителя** — полный канонический список (§6), не выборочно.

Итог — комментарий в issue с вердиктом: **approve** или **правки** (нумерованный
список). Максимум 2 итерации правок, дальше — эскалация координатору.

### 3.3. Слияние и приёмка
Координатор после approve: открывает PR из ветки поставки, сливает, гоняет полный
регресс **на результате слияния**, коммитит merge-post (что влито, что проверено),
обновляет очередь и статус-карточку. Владельцу — короткая сводка «что смотреть и что
решать». Продуктовое (вид, поведение, тексты) — только через приёмку владельца.
Инфраструктурное (CI, скрипты, доки процесса) координатор может принять сам,
уведомив владельца.

## 4. Что делать, если в задаче развилка

Развилка — это не твой выбор. Формулируешь оба варианта с последствиями, спрашиваешь
координатора (`❓ QUESTION`), и продолжаешь всё, что не зависит от ответа. Помечать
заметку в `workflow/decisions/` — когда решение принято.

## 5. Рабочий канон команды

Работа агентов идёт по общему канону команды: эталон — репо `bestdeejay-design/agents`
(PROTOCOL, WORKFLOW, BUS, BOARD, OPS + регламенты AGENT_RULES/COORDINATOR_RULES/
KNOWLEDGE_BASE/EXAMPLES), копия канона — в `workflow/` этого репо, проектная
конкретизация — `workflow/PROJECT.md`.

Ключевое (коротко):

- **Маркеры шины** — единственный язык сообщений между узлами: 👀 READ, 🎯 CONCLUSION,
  ✅ GATE OPEN, 🏁 DONE, 📬 DELIVERED, ✋ CLAIM, ⛔ BLOCKED, ❓ QUESTION, ♻️ RECLAIMED,
  📌 DECISION. Словарь — `workflow/KNOWLEDGE_BASE.md` §5.
- **Каждое сообщение — с подписью узла** («— Роль · сессия»): все работают под одним
  аккаунтом, личность — в подписи.
- **ARCA** (AUDIT → RESEARCH → CONCLUSION → ACTION → VERIFY) для size:M/L; гейт ACTION —
  только координатор; size:S — сокращённый цикл с approve-комментарием координатора.
- **Labels — правда.** Ровно один label из каждой закрытой группы (`status:`, `phase:`,
  `agent:`, `to:`, `type:`, `size:`, `priority:`, `env:`) плюс флаги. Переход label
  атомарный и всегда с маркером-комментарием первой строкой.
- **Задачи — issues.** Задачи без issue не существует.
- **Гигиена веток:** слитая ветка удаляется; база поставки — свежий `origin/main`.

## 6. Регресс — канонический список, без сокращений

```
swift build                 # сборка пакета (с ../ui)
swift test                  # PresentationTests + NativeWindowTests
./build.sh                  # продуктовый бандл DajetPlayer.app
```

Пуш — сразу после коммита, тем же дыханием. Красное на своей ветке — пуш откладывается:
сначала сверка базы (§2), только потом свой код. CI (`.github/workflows/build.yml`,
macos-15) дублирует это и добавляет бюджет бандла (15 МБ), zero-dep и сетевой запрет.

## 7. Границы (не твоя зона — не трогай)

- **`main`** — только координатор.
- **Версии и релизы** (`VERSION`, `CHANGELOG.md`, `Installer/`, `release.sh`, `tap.sh`) —
  только владелец.
- **Вид продукта** (оптика, темы, материалы, компоновка окна) — решение владельца;
  приёмка — окно на его обоях.
- **Слияние в `main` редактора** — только владелец.
- **Приватные репозитории** (`dajet/ui`, `dajet/editor`) — доступ выдаёт владелец;
  без доступа задача не берётся, а ставится вопрос.
- **Публичные контракты и существующие тесты** не ломать.

## 8. Коммуникация

- Координатор ↔ исполнитель/ревьювер: комментарии в issues (шина — `dajet/player`) и
  письма-комментарии в issue по шаблону `📬 DELIVERED`.
- Статус-карточка контура — `apps/HANDOFF.md` (обновляет координатор).
- Несогласие с решением — вопросом координатору, а не самодеятельностью в коде.
- Споры и неоднозначности — `❓ QUESTION` с вариантами и последствиями.

## 9. Слепые зоны

1. Локальный `.git` протух или откатился (бывали инциденты) — восстановиться с
   `origin`, потери ноль, инцидент письмом координатору.
2. Публичный контракт, который ты не можешь изменить, — спроси до кода.
3. Задача требует второго репозитория (`dajet/ui`, `dajet/editor`) — это другая сессия
   и другая задача; не пытайся прыгать между репозиториями.
